Copiar um objeto e separar o seu estado

Uma nova instância pode continuar a partilhar os objetos que guarda. Antes de escolher uma operação de cópia, identifique o estado que deve permanecer comum e o estado que deve evoluir separadamente.

01_Copy.kt↓ .ktPlayground ↗
data class Group(val names: MutableList<String>)

fun main() {
    val original = Group(mutableListOf("Ana"))
    val shared = original.copy()
    val separate = original.copy(names = original.names.toMutableList())
    shared.names.add("Rui")
    separate.names.add("Eva")
    println(original.names)
    println(shared.names)
    println(separate.names)
    println(original === shared)
    println(original.names === shared.names)
}

Saída esperada

[Ana, Rui]
[Ana, Rui]
[Ana, Eva]
false
true

A primeira chamada a copy() cria outro Group, mas mantém a referência à lista. A segunda recebe um argumento nomeado, names = ..., que substitui esse componente por uma lista criada com toMutableList().

MutableList<String> é uma lista modificável de textos; <String> indica o tipo dos elementos. add modifica a lista. As variáveis são val: não podemos reatribuir-lhes outras referências, mas podemos usar as operações de alteração dos objetos referidos.

=== compara identidade. As duas últimas linhas mostram que os objetos exteriores são distintos, embora um componente seja partilhado. Aqui, os elementos são textos imutáveis. Para elementos que sejam objetos mutáveis, copiar a lista não copia esses objetos: seria necessário decidir como copiar também cada elemento.

Escolher entre enum, object e companion object

Estas construções respondem a necessidades diferentes: alternativas fixas, uma instância partilhada e operações associadas à construção de instâncias. O exemplo reúne as três sem confundir as suas responsabilidades.

02_Construction.kt↓ .ktPlayground ↗
enum class RoomKind(val seats: Int) {
    SEMINAR(12), LAB(24)
}

object BookingRules {
    const val MAX_MINUTES = 120
    fun accepts(minutes: Int): Boolean = minutes in 1..MAX_MINUTES
}

class Booking private constructor(val minutes: Int) {
    companion object {
        fun create(minutes: Int): Booking {
            require(BookingRules.accepts(minutes))
            return Booking(minutes)
        }
    }
}

fun main() {
    val first = Booking.create(45)
    val second = Booking.create(45)
    println(RoomKind.SEMINAR.seats)
    println(first.minutes)
    println(first === second)
    println(BookingRules.accepts(121))
}

Saída esperada

12
45
false
false

RoomKind admite duas constantes, cada uma com uma capacidade. SEMINAR(12) fornece 12 ao parâmetro seats. O tipo é útil quando as alternativas são conhecidas e fixas.

object BookingRules disponibiliza uma instância partilhada. const val declara uma constante conhecida em compilação; aqui, o limite é um inteiro. in 1..MAX_MINUTES testa um intervalo com ambos os extremos incluídos.

private constructor impede a construção direta a partir do código exterior. Booking.create(45) chama a função do companion object; essa função verifica o argumento e chama o construtor. Cada chamada bem-sucedida cria uma nova reserva. O companion é partilhado; as reservas não são a mesma instância.

A regra foi escolhida apenas para este exemplo. No projeto, os limites devem resultar do problema que está a modelar.

03 / Diapositivos relacionados 12–28

Encapsulamento: preservar a capacidade de uma sala

Neste modelo, uma reserva ocupa um número de lugares numa sala. Não modelamos horários nem reservas simultâneas de salas completas. A propriedade central é simples: a ocupação deve permanecer entre zero e a capacidade.

03_Room.kt↓ .ktPlayground ↗
class Room(val capacity: Int) {
    init {
        require(capacity > 0)
    }
    var occupied: Int = 0
        private set
    val available: Int
        get() = capacity - occupied

    fun reserve(places: Int): Boolean {
        require(places > 0)
        if (places > available) return false
        occupied += places
        return true
    }

    fun release(places: Int) {
        require(places in 1..occupied)
        occupied -= places
    }
}

fun main() {
    val room = Room(3)
    println(room.reserve(2))
    println(room.reserve(2))
    room.release(1)
    println(room.occupied)
    println(room.available)
}

Saída esperada

true
false
1
2

init executa durante a construção. require(capacity > 0) rejeita uma capacidade inválida. A capacidade é uma propriedade val; a ocupação é uma propriedade var cujo private set impede alterações a partir de fora da classe.

available tem um getter calculado: cada leitura devolve capacity - occupied. Evitamos guardar um segundo estado que teria de ser atualizado em conjunto com a ocupação.

reserve distingue um argumento inválido, rejeitado por require, de um pedido positivo que não cabe, comunicado por false. A comparação ocorre antes da alteração. Em caso de sucesso, occupied += places soma os lugares e return true termina a chamada.

release só aceita um número de lugares entre 1 e a ocupação atual. Assim, uma libertação não pode produzir ocupação negativa. Este modelo pressupõe execução sequencial; a classe não acrescenta sincronização para acesso concorrente.

Experimente o estado da sala

Modelo sequencial de Room(6). Cada pedido aplica as mesmas verificações do programa.

04 / Diapositivos relacionados 68–85

Uma interface, duas formas de apresentar os mesmos dados

O código que pede um relatório não precisa de decidir como esse relatório é escrito. A interface fixa a operação disponível; cada implementação determina o resultado.

04_Reports.kt↓ .ktPlayground ↗
data class RoomSummary(val name: String, val available: Int)

interface RoomReport {
    fun render(room: RoomSummary): String
}

object CompactReport : RoomReport {
    override fun render(room: RoomSummary): String =
        "${room.name}: ${room.available}"
}

class SentenceReport(val prefix: String) : RoomReport {
    override fun render(room: RoomSummary): String =
        "$prefix ${room.name} tem ${room.available} lugares disponíveis."
}

fun show(room: RoomSummary, report: RoomReport) {
    println(report.render(room))
}

fun main() {
    val room = RoomSummary("A1", 3)
    show(room, CompactReport)
    show(room, SentenceReport("Sala"))
}

Saída esperada

A1: 3
Sala A1 tem 3 lugares disponíveis.

RoomSummary reúne os dados necessários para o relatório. RoomReport declara uma função que recebe esses dados e devolve uma String. A interface não guarda a ocupação da sala.

Os dois pontos em : RoomReport indicam implementação da interface. override assinala a implementação da operação declarada. CompactReport não precisa de configuração por instância; SentenceReport guarda um prefixo recebido no construtor.

show recebe o tipo da interface. A mesma chamada report.render(room) executa a implementação do objeto recebido. As expressões ${...} inserem valores calculados no texto; $prefix insere o valor da variável.

A operação devolve texto; a função show apresenta-o. Esta separação permite comparar resultados em testes sem depender da consola.

Exercício

Implemente um relatório CsvReport que devolva A1,3 para os mesmos dados. Acrescente uma chamada a show sem alterar a função show.

Ver resolução

A nova implementação satisfaz o mesmo contrato; show continua a receber RoomReport.

Ler um pedido sem confundir ausência, texto e número

A entrada do utilizador começa por ser texto. Converter esse texto e verificar o seu significado são passos diferentes. Uma função pequena permite testar ambos sem depender da leitura da consola.

05_Input.kt↓ .ktPlayground ↗
fun parsePlaces(text: String?): Int? {
    val places = text?.trim()?.toIntOrNull() ?: return null
    if (places <= 0) return null
    return places
}

fun main() {
    val inputs: List<String?> = listOf(" 2 ", "two", "0", null)
    for (text in inputs) {
        val places = parsePlaces(text)
        println(places ?: "Entrada inválida")
    }
}

Saída esperada

2
Entrada inválida
Entrada inválida
Entrada inválida

String? admite texto ou null; Int? admite um inteiro ou null. Neste exemplo, o resultado nulo representa um pedido que não foi possível interpretar como um número positivo de lugares.

?. só chama a operação seguinte quando existe um valor. trim() remove espaços exteriores; toIntOrNull() tenta converter o texto para um Int e devolve null quando a conversão falha, incluindo valores fora do intervalo de Int.

?: return null termina imediatamente a função quando a cadeia anterior produz null. Depois dessa linha, places é um Int. A verificação seguinte trata o significado do número: zero e valores negativos não são pedidos válidos neste modelo.

List<String?> é uma lista cujos elementos podem ser nulos. for (text in inputs) percorre-os. Na apresentação, places ?: "Entrada inválida" escolhe uma mensagem quando falta um resultado.

Exercício

06 / Diapositivos relacionados 18–28

Testar operações e invariantes

Um exemplo de utilização mostra um percurso. Um teste acrescenta uma expectativa explícita sobre o resultado e o estado final. Comecemos pelos limites: sala vazia, sala cheia e pedido recusado.

06_Checks.kt↓ .ktPlayground ↗
class Room(val capacity: Int) {
    init {
        require(capacity > 0)
    }
    var occupied: Int = 0
        private set
    val available: Int
        get() = capacity - occupied

    fun reserve(places: Int): Boolean {
        require(places > 0)
        if (places > available) return false
        occupied += places
        return true
    }

    fun release(places: Int) {
        require(places in 1..occupied)
        occupied -= places
    }
}

fun main() {
    val room = Room(3)
    check(room.occupied == 0)
    check(room.reserve(3))
    check(room.available == 0)
    check(!room.reserve(1))
    check(room.occupied == 3)
    room.release(3)
    check(room.occupied == 0)
    check(room.available == 3)

    var rejected = false
    try {
        room.reserve(0)
    } catch (error: IllegalArgumentException) {
        rejected = true
    }
    check(rejected)
    check(room.occupied == 0)
    println("Todas as verificações foram satisfeitas.")
}

Saída esperada

Todas as verificações foram satisfeitas.

O programa repete a classe Room para poder ser executado isoladamente. check(condition) verifica uma condição e lança IllegalStateException quando ela é falsa. Uma execução bem-sucedida chega à mensagem final.

! inverte um Boolean. check(!room.reserve(1)) exige que a reserva falhe quando a sala está cheia. A linha seguinte verifica também que essa falha não alterou a ocupação.

O bloco try contém uma chamada que deve recusar o argumento zero. catch (error: IllegalArgumentException) trata precisamente essa exceção. A variável rejected permite confirmar que a recusa aconteceu.

Os testes cobrem percursos escolhidos, não constituem uma prova para todas as execuções. A justificação do invariante acompanha a leitura das operações: construção válida, reserva que não excede os lugares livres e libertação que não excede os lugares ocupados.

Exercício

07 / Diapositivos relacionados 68–88

Continuação: representar resultados com dados diferentes

Um Boolean comunica sucesso ou insucesso. Quando cada resultado precisa de informação diferente, podemos dar um tipo próprio a cada caso e reuni-los numa interface sealed.

07_Outcomes.kt↓ .ktPlayground ↗
sealed interface BookingResult

data class Accepted(val remaining: Int) : BookingResult
data class Rejected(val reason: String) : BookingResult

fun request(available: Int, wanted: Int): BookingResult {
    require(available >= 0)
    require(wanted > 0)
    return if (wanted <= available) {
        Accepted(available - wanted)
    } else {
        Rejected("Lugares insuficientes")
    }
}

fun describe(result: BookingResult): String = when (result) {
    is Accepted -> "Aceite; lugares restantes: ${result.remaining}"
    is Rejected -> "Recusado: ${result.reason}"
}

fun main() {
    println(describe(request(3, 2)))
    println(describe(request(3, 4)))
}

Saída esperada

Aceite; lugares restantes: 1
Recusado: Lugares insuficientes

BookingResult é o tipo comum. Accepted guarda os lugares restantes; Rejected guarda uma justificação. As duas classes usam : BookingResult para implementar a interface.

sealed restringe as implementações diretas à mesma unidade de módulo e ao mesmo pacote. Neste ficheiro, os dois casos diretos são data classes, que não podem ser herdadas. O compilador conhece, por isso, as alternativas que o when precisa de tratar.

when (result) é uma expressão: cada ramo fornece uma String. is Accepted testa o tipo e permite consultar result.remaining nesse ramo. O mesmo acontece com Rejected e reason. Como os casos estão cobertos, não é necessário else.

request calcula uma resposta; não altera uma sala. Recebe uma disponibilidade e produz um resultado. Integrar este resultado num objeto mutável exige manter a verificação e a atualização coordenadas, como na classe Room anterior.

Exercício

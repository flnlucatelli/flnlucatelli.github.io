Copying an object and separating its state

A new instance can still share the objects it stores. Before choosing a copying operation, identify the state that should remain shared and the state that should evolve separately.

01_Copy.kt↓ .ktPlayground ↗
data class Group(val names: MutableList<String>)

fun main() {
    val original = Group(mutableListOf("Ana"))
    val shared = original.copy()
    val separate = original.copy(names = original.names.toMutableList())
    shared.names.add("Rui")
    separate.names.add("Eva")
    println(original.names)
    println(shared.names)
    println(separate.names)
    println(original === shared)
    println(original.names === shared.names)
}

Expected output

[Ana, Rui]
[Ana, Rui]
[Ana, Eva]
false
true

The first call to copy() creates another Group but retains the list reference. The second supplies a named argument, names = ..., replacing that component with a list created by toMutableList().

MutableList<String> is a mutable list of strings; <String> specifies the element type. add modifies the list. The variables are val: we cannot reassign them to other references, but we can use the mutation operations offered by the objects they refer to.

=== compares identity. The final two lines show that the outer objects differ while one component is shared. The elements here are immutable strings. If the elements were mutable objects, copying the list would not copy those objects: we would need to decide how to copy each element as well.

02 / Related slides 43–67

Choosing between enum, object and companion object

These constructs address different needs: fixed alternatives, one shared instance, and operations associated with creating instances. This example combines all three while keeping their responsibilities distinct.

02_Construction.kt↓ .ktPlayground ↗
enum class RoomKind(val seats: Int) {
    SEMINAR(12), LAB(24)
}

object BookingRules {
    const val MAX_MINUTES = 120
    fun accepts(minutes: Int): Boolean = minutes in 1..MAX_MINUTES
}

class Booking private constructor(val minutes: Int) {
    companion object {
        fun create(minutes: Int): Booking {
            require(BookingRules.accepts(minutes))
            return Booking(minutes)
        }
    }
}

fun main() {
    val first = Booking.create(45)
    val second = Booking.create(45)
    println(RoomKind.SEMINAR.seats)
    println(first.minutes)
    println(first === second)
    println(BookingRules.accepts(121))
}

Expected output

12
45
false
false

RoomKind has two constants, each with a capacity. SEMINAR(12) supplies 12 to the seats parameter. This type is useful when the alternatives are known and fixed.

object BookingRules provides one shared instance. const val declares a compile-time constant; the limit here is an integer. in 1..MAX_MINUTES tests a range containing both endpoints.

private constructor prevents direct construction from external code. Booking.create(45) calls the function in the companion object; that function validates the argument and invokes the constructor. Each successful call creates a new booking. The companion is shared; the bookings are distinct instances.

This rule was chosen for the example. In a project, the limits should follow from the problem being modelled.

03 / Related slides 12–28

Encapsulation: preserving a room’s capacity

In this model, a reservation occupies a number of places in a room. We are not modelling timetables or simultaneous bookings of entire rooms. The central property is simple: occupancy must stay between zero and capacity.

03_Room.kt↓ .ktPlayground ↗
class Room(val capacity: Int) {
    init {
        require(capacity > 0)
    }
    var occupied: Int = 0
        private set
    val available: Int
        get() = capacity - occupied

    fun reserve(places: Int): Boolean {
        require(places > 0)
        if (places > available) return false
        occupied += places
        return true
    }

    fun release(places: Int) {
        require(places in 1..occupied)
        occupied -= places
    }
}

fun main() {
    val room = Room(3)
    println(room.reserve(2))
    println(room.reserve(2))
    room.release(1)
    println(room.occupied)
    println(room.available)
}

Expected output

true
false
1
2

init runs during construction. require(capacity > 0) rejects an invalid capacity. Capacity is a val property; occupancy is a var property whose private set prevents changes from outside the class.

available has a computed getter: each read returns capacity - occupied. This avoids storing a second piece of state that would have to be updated together with occupancy.

reserve distinguishes an invalid argument, rejected by require, from a positive request that does not fit, reported by false. The comparison precedes the update. On success, occupied += places adds the places and return true ends the call.

release accepts only a number of places between 1 and the current occupancy. Releasing places therefore cannot produce negative occupancy. This model assumes sequential execution; the class does not add synchronisation for concurrent access.

Explore the room’s state

A sequential model of Room(6). Every request applies the same checks as the program.

04 / Related slides 68–85

One interface, two presentations of the same data

Code that requests a report need not decide how that report is written. The interface fixes the available operation; each implementation determines its result.

04_Reports.kt↓ .ktPlayground ↗
data class RoomSummary(val name: String, val available: Int)

interface RoomReport {
    fun render(room: RoomSummary): String
}

object CompactReport : RoomReport {
    override fun render(room: RoomSummary): String =
        "${room.name}: ${room.available}"
}

class SentenceReport(val prefix: String) : RoomReport {
    override fun render(room: RoomSummary): String =
        "$prefix ${room.name} has ${room.available} places available."
}

fun show(room: RoomSummary, report: RoomReport) {
    println(report.render(room))
}

fun main() {
    val room = RoomSummary("A1", 3)
    show(room, CompactReport)
    show(room, SentenceReport("Room"))
}

Expected output

A1: 3
Room A1 has 3 places available.

RoomSummary collects the data needed by the report. RoomReport declares a function that receives those data and returns a String. The interface does not store room occupancy.

The colon in : RoomReport declares implementation of the interface. override marks the implementation of its operation. CompactReport needs no per-instance configuration; SentenceReport stores a prefix supplied to its constructor.

show accepts the interface type. The same call, report.render(room), executes the implementation of the object received. Expressions ${...} insert computed values into a string; $prefix inserts the variable’s value.

The operation returns text; show displays it. This separation allows tests to compare results without depending on console output.

05 / Related slides 86–88

Reading a request without confusing absence, text and numbers

User input starts as text. Converting that text and validating its meaning are different steps. A small function lets us test both without depending on console input.

05_Input.kt↓ .ktPlayground ↗
fun parsePlaces(text: String?): Int? {
    val places = text?.trim()?.toIntOrNull() ?: return null
    if (places <= 0) return null
    return places
}

fun main() {
    val inputs: List<String?> = listOf(" 2 ", "two", "0", null)
    for (text in inputs) {
        val places = parsePlaces(text)
        println(places ?: "Invalid input")
    }
}

Expected output

2
Invalid input
Invalid input
Invalid input

String? admits a string or null; Int? admits an integer or null. Here, a null result means that the request could not be interpreted as a positive number of places.

?. calls the next operation only when a value exists. trim() removes surrounding whitespace; toIntOrNull() attempts conversion to Int and returns null on failure, including values outside the range of Int.

?: return null immediately ends the function when the preceding chain produces null. After that line, places is an Int. The next check concerns the number’s meaning: zero and negative values are not valid requests in this model.

List<String?> is a list whose elements may be null. for (text in inputs) visits them. In the output, places ?: "Invalid input" chooses a message when there is no result.

06 / Related slides 18–28

Testing operations and invariants

An example demonstrates one path through a program. A test adds an explicit expectation about the result and final state. Start with the boundaries: an empty room, a full room and a rejected request.

06_Checks.kt↓ .ktPlayground ↗
class Room(val capacity: Int) {
    init {
        require(capacity > 0)
    }
    var occupied: Int = 0
        private set
    val available: Int
        get() = capacity - occupied

    fun reserve(places: Int): Boolean {
        require(places > 0)
        if (places > available) return false
        occupied += places
        return true
    }

    fun release(places: Int) {
        require(places in 1..occupied)
        occupied -= places
    }
}

fun main() {
    val room = Room(3)
    check(room.occupied == 0)
    check(room.reserve(3))
    check(room.available == 0)
    check(!room.reserve(1))
    check(room.occupied == 3)
    room.release(3)
    check(room.occupied == 0)
    check(room.available == 3)

    var rejected = false
    try {
        room.reserve(0)
    } catch (error: IllegalArgumentException) {
        rejected = true
    }
    check(rejected)
    check(room.occupied == 0)
    println("All checks passed.")
}

Expected output

All checks passed.

The program repeats the Room class so it can run independently. check(condition) tests a condition and throws IllegalStateException when it is false. A successful run reaches the final message.

! negates a Boolean. check(!room.reserve(1)) requires the reservation to fail when the room is full. The next line also verifies that this failure did not change occupancy.

The try block contains a call that should reject zero as an argument. catch (error: IllegalArgumentException) handles that specific exception. The rejected variable records whether rejection occurred.

Tests cover selected paths; they do not prove a property for every execution. Justifying the invariant requires reading the operations: valid construction, reservation that does not exceed free places, and release that does not exceed occupied places.

07 / Related slides 68–88

Further step: representing outcomes with different data

A Boolean communicates success or failure. When each outcome needs different information, we can give each case its own type and bring them together through a sealed interface.

07_Outcomes.kt↓ .ktPlayground ↗
sealed interface BookingResult

data class Accepted(val remaining: Int) : BookingResult
data class Rejected(val reason: String) : BookingResult

fun request(available: Int, wanted: Int): BookingResult {
    require(available >= 0)
    require(wanted > 0)
    return if (wanted <= available) {
        Accepted(available - wanted)
    } else {
        Rejected("Not enough places")
    }
}

fun describe(result: BookingResult): String = when (result) {
    is Accepted -> "Accepted; remaining: ${result.remaining}"
    is Rejected -> "Rejected: ${result.reason}"
}

fun main() {
    println(describe(request(3, 2)))
    println(describe(request(3, 4)))
}

Expected output

Accepted; remaining: 1
Rejected: Not enough places

BookingResult is the common type. Accepted stores the remaining places; Rejected stores a reason. Both classes use : BookingResult to implement the interface.

sealed restricts direct implementations to the same module and package. In this file, both direct cases are data classes, which cannot be subclassed. The compiler therefore knows the alternatives that the when expression must handle.

when (result) is an expression: each branch provides a String. is Accepted tests the type and allows access to result.remaining in that branch. The same applies to Rejected and reason. Because the cases are covered, no else is needed.

request calculates a response; it does not modify a room. It receives an availability and produces a result. Integrating this result into a mutable object requires coordinating validation and update, as in the earlier Room class.
